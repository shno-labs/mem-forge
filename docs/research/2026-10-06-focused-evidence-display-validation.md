# Selected Evidence and focused display validation

Status: Bounded iteration complete. Both independent reviews fail accepted extraction gates; no adoption or production cutover.

The user accepts existing selectable block granularity, including table rows,
and requests focused, near-original Evidence wording generated with the
Primary/Required selection. The [proposed design](../design/claim-evidence-focused-display.md)
keeps the original source block as provenance and correspondence authority,
with generated display separate and no mandatory public LLM label. Occasional
display errors are acceptable; no numerical display-error threshold is agreed.
Claim correctness, selected-Primary suitability, useful coverage and selected
Required relevance remain separate criteria.

## Executed mechanics

Ten local checks passed on the exact candidate prototype:

- Generated display accounts for the selected refs exactly once.
- Actual production planner, runner, selector resolution and result assembly
  retain identical authoritative Evidence when display wording differs,
  including deliberately incorrect test wording. This proves separation, not
  that the wording is true.
- Recording preserves actual SAP placeholder prompt values and schema without
  copying binding credentials or headers.
- Complete native Confluence input with controlled unchanged, moved, duplicate,
  modified and governing-context variants follows expected correspondence and
  Change Impact routes. These are controlled fixtures, not authentic consecutive
  provider-revision acceptance.

No product Python implementation, storage protocol, UI or Cloud adapter was
changed for this pilot. A process-local prompt/schema injection exercises the
real adapters, planner, runner, structured client, selector resolution and
assembly. Display capture is a private evaluation record, not a persisted
product field or proof of `get_memory` integration.

## Acceptance scope

Blind assessment must inspect every candidate/ref/display and every frozen
inventory atom. The accepted extraction gates remain zero major claim or
selected-Primary errors, at least 95% fully covered useful core knowledge per
source, and at least 95% relevant/nonredundant selected Required. Supplementary
recall is best effort. Display fidelity, retained conditions, readability and
length are reported separately. A correct binding is not semantic support.

This prototype failed extraction acceptance. Display storage/API/UI integration,
authentic consecutive revisions, complete lifecycle/storage adapter parity and
CF deployment verification remain outside this experiment's acceptance scope.

## Conclusion and disposition

The combined mechanism can retain static source-block binding while generating
focused readable evidence in one model response. It did not require finer table
cells or generated-text matching. All static source checks succeeded, yet
modality, useful standalone coverage and ref-role selection still failed. Thus
these observed failures are not failed exact-coordinate resolution; they occur
in claim generation and semantic selection. This experiment does not isolate
prompt/schema/task-design effects from model reasoning or prove an intrinsic
Sonnet ceiling. It cannot establish that no complete design is feasible.

Stop this iteration without a prompt patch/retry loop, semantic repair, candidate
pruning, product integration or deployment. Preserve all failed outputs and
produce the updated handoff the user requested if this iteration still failed.
The proposed design remains unaccepted as a complete extraction scheme. The
next collaborator should start from the exact semantic contract and task
boundary, retaining the successful source/display separation as evidence,
before proposing another frozen design. No additional paid canary is justified
without a named design hypothesis.
