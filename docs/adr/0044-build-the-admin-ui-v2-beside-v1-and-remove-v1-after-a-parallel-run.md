# Build the admin UI V2 beside V1 and remove V1 after a parallel run

Status: Accepted

Date: 2026-09-29

## Context

The admin UI (`admin-ui/`) is the one browser surface of MemForge. OSS serves
it from its own nginx container (`admin-ui/Dockerfile`, `compose.yaml`), and
Cloud serves it at `/` from the cloud service after composing it with the
Cloud extension (`memforge-cloud/packages/admin-cloud-ext`,
`scripts/compose-admin-ui.mjs`, `routes/admin_ui.py`).

A design review on 2026-09-29 redesigned every page (navigation, Sources,
Source setup, Memories, Review, Evaluation, Projects, Settings and the Cloud
admin pages) and confirmed each change. Carrying it out inside `admin-ui/`
would rewrite most views in place, and several parts of the current package
make that expensive:

- Only nine primitives exist (`components/ui`). There is no shared table,
  filter bar, detail drawer, property list or confirmation dialog, so each view
  builds its own.
- The Cloud extension may not import OSS components. It keeps its own
  `CloudTable`, `CloudPageChrome`, `CloudLink` and `ErrorBanner`, which drift
  from the OSS equivalents.
- Response types are written by hand in `api/types.ts` and have drifted from
  the backend: memory search sends `sources` while the API expects
  `source_filter.source_ids`, and the standalone local-agent base URL is
  `/api/v1/cloud/local-agent` while the router is mounted at
  `/api/cloud/local-agent`.
- `npm test` chains 27 scripts, most of which compile one file with `tsc` and
  run it with `node`, and many of them assert on source text.
- The extension contract exists twice (`admin-ui/src/extension.ts` and Cloud's
  `extension-contract.ts`) and the copies disagree: the OSS copy reserves
  `schedules`, the Cloud copy does not.
- The Cloud extension declares React 18 and React Router 6 while it runs inside
  the OSS bundle on React 19 and React Router 7.

## Decision

### A separate package that runs beside V1

The redesign is a new package, `admin/` (`@memforge/admin`), next to
`admin-ui/`. V1 keeps its routes, build and deployment unchanged and receives
only security and data-loss fixes. V2 is served under `/v2/`:

- Vite `base` and the router `basename` are both `/v2/`, set in one constant
  (`APP_BASE_PATH`).
- OSS development runs V1 on port 5174 and V2 on port 5175; the V2 dev server
  forwards every path outside `/v2/` and `/api/` to the V1 dev server. The
  image (`admin/Dockerfile`, `admin/nginx.conf`) builds both bundles and serves
  V2 from `/v2/` with its own `index.html` fallback.
- Cloud composes both bundles and serves V2 from `/v2/` beside V1 at `/`.
- While a page is not built in V2, its sidebar item opens the V1 page, so users
  can work in V2 from the first release. Every sidebar page is now built in V2.
  Adding and configuring a source still opens the V1 Sources page until V2 has
  its own source setup. Renewing a Jira browser session runs directly in V2
  through the existing `jira_auth` local daemon job. The page waits for durable
  completion, reports failure, and refreshes source readiness; enqueueing a
  job does not mean sign-in succeeded. Creation uses the selected workspace's
  local-agent route. Reading an admitted job uses the host route keyed by job
  ID, whose authorization validates its recorded workspace and caller.
  While the page remains open, a failed status read retains the admitted job
  ID so a retry resumes that read instead of enqueueing another sign-in.

The package is named for what it is, not for its version, so nothing needs a
rename when V1 is gone. "V2" names the migration, not the code.

### Technology

| Concern | Choice |
|---|---|
| Framework and build | React 19, Vite 8, TypeScript strict |
| Styling | Tailwind CSS v4 with every color, radius and font as a CSS variable (`src/styles/tokens.css`); light and dark themes |
| Primitives | shadcn/ui on Base UI, copied into `src/ui` and owned by this repository |
| Server state | TanStack Query, with query keys per feature |
| Tables | TanStack Table behind one `DataTable` pattern |
| Forms | React Hook Form with Zod schemas |
| API access | `openapi-fetch` over types generated by `openapi-typescript` from the FastAPI OpenAPI document |
| Routing | React Router 7 |
| Notifications | sonner |
| Icons | lucide-react, plus source brand marks |
| Component catalogue | Storybook, for `ui` and `patterns` only |
| Tests | Vitest and Testing Library for units and components, Playwright for a small end-to-end smoke suite |

API types come from the backend. `scripts/export_openapi.py` writes the
OpenAPI document of `create_admin_app` to `admin/openapi/admin.json`,
`npm run gen:api` regenerates `src/api/schema.gen.ts` from it, and CI fails
when either committed file is stale. HEAD operations are left out: FastAPI
gives a GET and HEAD route one operation id, and the UI never sends HEAD.

71 of the 119 operations still declare no response model, so their generated
response type is `unknown`. V2 adds response models to the routes a page uses
before building that page, as the Sources page routes already have. Where a
schema leaves part of a body free-form (a local agent job's `result`),
`src/api/responses.ts` declares the fields the UI reads and `src/api/paths.ts`
merges them into the generated paths, so every call stays typed through one
client. A response model on a shared route also validates what Cloud's HANA
adapter returns, so adding one is checked against Cloud first.

### Layers

```
src/styles     tokens and global CSS
src/ui         primitives: Button, Dialog, Menu, Select, Switch, Tabs, ...
src/patterns   product-neutral compositions: DataTable, FilterBar,
               DetailDrawer, PropertyList, StatusBadge, EmptyState,
               ConfirmDialog, PageHeader, GroupHeader
src/features   one folder per product area: api hooks, components, routes
src/app        shell (sidebar, topbar), router, extension registry
src/api        generated schema, typed client, workspace target
src/lib        pure helpers with no React
```

A layer imports only from layers below it: `features` may use `patterns`, `ui`,
`api` and `lib`; `patterns` may use `ui` and `lib`; `ui` may use `lib`. A
feature exposes its public API in its `index.ts`, and other features import
only from there (the Sources page reads local sync status from
`@/features/local-sync`). ESLint (`no-restricted-imports`) enforces these
rules and rejects any import from `admin-ui/`. Pure logic lives in plain `.ts`
modules under the feature's `model/` folder and is tested without React.

`DataTable` columns are defined at module level. Cell functions render as
components, so columns rebuilt on each render would remount every row on each
poll; cells that need page state read it from a feature context.

V1 modules that are pure and correct (source sync activity, readiness, list
organization, project grouping, brand marks) are copied into V2 with their
behavior tests ported to Vitest. V1 tests that assert on source text are not
ported. V2 never imports from `admin-ui/`, so deleting V1 cannot break V2.

### Extension contract

V2 publishes four entry points through the package `exports` map:

- `@memforge/admin/app`, whose `renderAdminApp(element, extension)` is what the
  Cloud composed build calls instead of mutating a module-level registry;

- `@memforge/admin/ui` and `@memforge/admin/patterns`, which the Cloud extension
  uses instead of its own table, page chrome, link and error banner;
- `@memforge/admin/extension`, the only copy of the extension contract.

The contract keeps routes, navigation items, topbar slots, the shell wrapper
and reserved-route redirects. Navigation items gain a `placement` so Cloud admin
renders at the bottom of the sidebar below a divider. The account surface is
the topbar menu only; V2 has no sidebar identity card. The workspace switcher is
a topbar slot. The extension declares React, React Router, TanStack Query and
`@memforge/admin` as peer dependencies with the host's versions.

### Marking what exists only for V1

Code that must stay while V1 runs, but that V2 does not use and that should not
survive V1, carries the tag `admin-ui-v1`:

- TypeScript: a `@deprecated admin-ui-v1: <reason>` JSDoc tag.
- Python: a `Deprecated (admin-ui-v1): <reason>` comment, and `deprecated=True`
  on FastAPI routes and Pydantic fields so the OpenAPI document shows it.
- Build and deployment files: a `Deprecated (admin-ui-v1)` comment.

`git grep -n "admin-ui-v1"` lists everything to delete with V1. Marked today:

- `PUT /api/v1/memories/{id}`, which retires with a fixed reason and no content
  hash, visibility check or actor; V2 uses `POST /memories/{id}/retire`.
- The project `kind` field (`normal` or `shared`) on create, update and
  response. Ranking and access read only the reserved `SHARED` key, so the field
  changes a label and nothing else. Removing it also removes `is_shared` from
  the storage protocol and both store adapters.
- In V1: the active-project state and its chip and banner, the Scheduled Syncs
  page, the unwired theme and notification buttons, the reserved `schedules`
  segment, the `accountSurface.sidebarFooter` slot, `ProjectKind` and the
  memory detail page's call to `PUT /memories/{id}`.
- Build and CI: the V1 stage in `admin/Dockerfile`, the V1 location in
  `admin/nginx.conf`, the V1 dev proxy in `admin/vite.config.ts`, the
  `admin-ui` CI job and the V1 half of each `ui-*` Makefile target.
- In V2: `V1_SOURCES_PATH` and `openInV1`, which open the V1 Sources page to add,
  configure or repair connections other than Jira browser-session renewal.
  V2's own source setup replaces them.

Apart from its links to the V1 Sources page, V2 must not read or write anything
tagged `admin-ui-v1`.

### Cut-over and removal

V2 replaces V1 when every item of the implementation checklist is built, the
Cloud composed build serves V2 and a full release cycle has passed with no open
defect that exists only in V2. Then:

1. V2 moves to `/` and V1 to `/v1/` for one release, so bookmarks keep working.
2. `admin-ui/` is deleted with everything tagged `admin-ui-v1`, including the
   storage column behind project `kind` through a migration in OSS and in the
   HANA adapter.
3. `APP_BASE_PATH` becomes `/`.

## Cloud impact

- **Composition.** `compose-admin-ui.mjs` builds both packages and emits two
  dist directories. `routes/admin_ui.py` mounts the V2 dist at `/v2/` with its
  own SPA fallback before the V1 mount at `/`. The Tailwind `@source` hints
  that the script injects must include the V2 source tree.
- **Extension.** The Cloud extension moves to `@memforge/admin/extension` and
  imports `@memforge/admin/ui` and `@memforge/admin/patterns`. Its own
  `CloudTable`, `CloudPageChrome`, `CloudLink`, `ErrorBanner` and
  `SidebarAccountFooter` are deleted when V1 is removed. The single-UI extension
  design (`docs/specs/2026-06-07-memforge-cloud-single-ui-extension-design.md`)
  must be updated to allow these imports. React, React Router and TanStack Query
  become peer dependencies at the host's versions.
- **Data plane.** No API changes. V2 calls the same `/api/v1` routes with the
  same `workspace_id` parameter. Cloud's management API under
  `/api/cloud/management` gets generated types the same way from the cloud
  service's OpenAPI document.
- **Storage.** Nothing changes until V1 is removed. Then the project `kind`
  field goes away, so `create_project` and `update_project` in
  `storage/adapters/protocols.py` lose their `is_shared` argument, and the HANA
  workspace adapter (`IS_SHARED` column and its CRUD) and
  `core-integration/workspace_database.py` must change with it.

## Consequences

- Two admin bundles ship during the parallel run, and fixes that touch both
  need care. V1 accepts only security and data-loss fixes to keep this small.
- Generated API types turn backend contract drift into build errors.
- Cloud stops maintaining a second set of primitives.
- The `admin-ui-v1` tag makes the removal a mechanical search.
