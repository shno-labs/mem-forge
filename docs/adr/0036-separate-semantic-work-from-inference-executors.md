# ADR 0036: Separate semantic work from inference executors

## Status

Accepted as target design. Implementation is deferred. The LLM batch runner is the first step of Cloud issue #505, whose first PR delivers it and moves the existing call sites onto it; #505 also tracks the Support and Relation semantics. Cloud issue #506 builds on the runner with the executor interfaces, classifier backends, their evaluation (Jev included) and prompt caching.

## Context

The shared structured client currently exposes open-vocabulary generation,
closed-set classification, ranking, semantic verification and Evidence selection
through one provider-shaped interface. Domain callers render prompt strings
before the transport seam. This makes repeated revision context difficult to
reuse, obscures which calls are classifiers, and couples application work to one
generative model contract.

Large revision workloads also repeat stable instructions and current Source
context across claim cohorts. Provider prompt caching can reduce that transport
cost only when stable prefix material is deliberately ordered before changing
cohort and retry material. Cache behavior must remain an optimization rather
than execution state.

TypeSafe/Jev supplies fast typed Choice, Noul and Score judgments over shared
text state. It does not generate open-vocabulary claims or explanations, does
not currently accept images, and evaluates questions in one request
independently. Treating it as another generic chat model would leak those
differences into callers or silently weaken existing contracts.

## Decision

1. Domain planners return an immutable backend-neutral `ContextBundle` plus either `GenerationWork` or `JudgmentWork`. Authority, selectability, exact references, access identity and complete manifests remain application-owned.
2. `GenerationExecutor` handles open-vocabulary output and dependent multi-field proposals. Claim Extraction, candidate admission and complete Support Assessment use it. `JudgmentExecutor` handles complete-input, closed-label, independent classification or ranking. Its configured classifier model may be TypeSafe/Jev or a small-parameter LLM that satisfies the same application contract.
3. Classifier eligibility is granted for an entire task contract from a fixed evaluation suite. Runtime probabilities are diagnostic only. There is no per-item confidence fallback, hidden LLM substitution or provider cascade. A missing or invalid row gets one re-ask of just its item (decision 13); it never falls back to another backend. A Change Impact execution failure routes the affected claim to Support Assessment; it is never recorded as a label.
4. Change Impact Classification is eligible judgment work. It receives one fixed claim and one capacity-safe `ChangeBundle`, and returns `AFFECTED` or `UNAFFECTED`. It runs on the existing Structured LLM until a classifier backend passes the task's evaluation. A change containing a global statement with unclear scope ("the process above", "this document", "discontinued from a given date") is `AFFECTED`; this rule has no dedicated evaluation cases. Multiple groups should share one bundle when they fit; multiple bundles are OR-reduced by code. Routing is per whole Support: any `UNKNOWN` part is application-owned `UNRESOLVED(partial_coverage)` and KEEP; any `MODIFIED`, `REMOVED` or `AMBIGUOUS` part bypasses this classifier and enters Support Assessment; when all parts are `EXACT_UNCHANGED`, a revision without changed content rebinds without a model call and a revision with changed content goes through Change Impact. Removed content counts as changed content: the `ChangeBundle` carries the old text of removed ReadingGroups, so a distant qualifier that was deleted is visible.
5. Same-Unit Relation is sparse Structured-LLM work. After deterministic exact matches, it receives admitted Candidates, each Candidate's current Evidence and the Claims of all Active same-Unit old Memories. It receives no Support result and checks no Evidence entailment; candidate admission owns that check. It returns one row per Candidate listing only meaningful relations; omission means "no relation proposed", while a missing row, unknown ID or truncation is an execution failure. A pairwise classifier backend would need its own contract and evaluation. Partitioning is a transport detail and cannot alter coverage, atomicity or business state. Cross-document relation discovery remains bounded retrieval followed by classification over `K` pairs.
6. Complete Support Assessment remains compound `GenerationWork`. `EvidenceFragment`, `ReadingGroup`, `AssessmentContext` and `AssessmentScope` are distinct. The deterministic planner only orders reading: Support Assessment streams the complete current content in a fixed order. The first part holds every changed ReadingGroup (added, modified, and removed ones as read-only old text) and the ReadingGroups that hold that item's own prior Evidence, so the first part is per item; the rest follows. No item exits while any ReadingGroup of the first part is unread; after the first part, each item exits as soon as it has complete Support; only an item that read the whole order under authoritative coverage of the affected objects may finalize `UNSUPPORTED`. There is no cost comparison and no start decision. The final semantic result is therefore `SUPPORTED(primary_ref, required_refs[]) | UNSUPPORTED`, while incomplete coverage or execution is the separate application result `UNRESOLVED(reason)`. The planner sends old exact excerpt only for `MODIFIED`, `REMOVED` and `AMBIGUOUS`; `EXACT_UNCHANGED` uses current material, while `UNKNOWN` does not invoke the model.
7. `REBIND_SUPPORT` preserves Memory identity and claim, materializes or reuses target-Revision Evidence, and atomically attaches the new Support assertion while marking the replaced assertion inactive. Prior Support rows, Evidence and lifecycle history remain immutable and auditable.
8. Structured LLM prompt caching supports two deterministic layouts. `REVISION_FIRST` evidence-fixed work places the current catalog before changing Memory cohorts; `COHORT_FIRST` cohort-fixed streaming places fixed unresolved claims before changing AssessmentContexts. The selected work plan declares one layout and retries preserve it. Early exit and LLM batch runner splits change later prefixes; a cache miss is acceptable. Cache identity and retention never affect correctness.
9. Classifier adapters render shared state plus independent closed-label questions. Jev gains efficiency from shared in-request state and parallel questions; no cross-request Jev prompt cache is assumed. A small-model LLM adapter must return the identical application schema.
10. Provider results remain proposals. Exact selector validation, complete coverage, Source authority, destructive validation, lifecycle reduction and atomic stale-guarded commit remain application-owned.
11. Streamed Support output carries only current `witness_delta` additions. Application code validates and monotonically union-merges them into supporting/opposing witness sets; every carried ref is rehydrated with exact current text and Primary eligibility in the next call. The model cannot drop an earlier witness by omission and does not emit cumulative Support status. `UNRESOLVED` is an execution result, not a lifecycle state.
12. Support Assessment exclusively owns the single ordered read. `DestructiveValidation` verifies the completed ordered-read receipt, coverage, manifests, witnesses, active-Support count and stale guards; it never runs a duplicate semantic scan.
13. Every model call goes through one LLM batch runner (code sketch `LlmBatchRunner`), for generation and judgment alike and for Structured LLM and classifier backends alike. The caller supplies fixed work items with stable IDs, shared context as an ordered list of separable parts, the prompt contract and response schema, and a decoder. When the shared context has to be chunked, the runner returns one result per item and chunk and the caller merges them (Change Impact: OR; Sparse Relation: union); the runner never receives merge rules. The runner owns capacity fit from LiteLLM metadata capped by the existing `MEMFORGE_LLM_MAX_*` overrides, packing into transport requests, bounded concurrency, per-row acceptance with one re-ask of the rejected rows, exact coverage and ID validation, and typed per-item failures. There are no per-task item or character caps; the only other limits are ones a backend adapter declares, such as Jev's Choice option count. A request with several items that ends in `deadline_exceeded`, `input_capacity_exceeded`, a provider 413 `payload_too_large` or truncated output (`finish_reason=length`) is a capacity failure: the runner splits it in half and resends each half until they complete; truncated output is not resent as JSON text at the same `max_tokens`. The model returns one row per item, and the task's decoder validates every row on its own. Valid rows are accepted at once and never sent again. The items whose rows are rejected or missing are re-asked once, together, in one smaller request that holds only them and names each item's exact error (for example "NEW-0003 names MEM-0037, which is not in its allowed list"); the re-ask is packed by capacity, and in a Support chain it reads the same step from the same position with the items' unchanged carried state. A request with k rejected rows therefore costs one extra call, whatever k and the request size. A request is split in half only when the failing item cannot be named: on a capacity failure, and when its output cannot be read into rows at all (malformed or ambiguous JSON, or a schema failure), after one correction of the whole request. A Support chain step holding a single Claim that spans several ReadingGroups first halves its ReadingGroups on a capacity failure. A single item that still fails is a typed failure with diagnostics. It is unjudgeable in isolation in exactly two cases: the item alone exceeds the route's input capacity (from the capacity fit, `input_capacity_exceeded` or a provider 413), or a model response for it was received and still fails validation after its one re-ask or correction (malformed or ambiguous JSON included). Every other failure is not: a transient provider error or timeout, a request the provider rejects (such as a 400) and an unexpected exception. One rule gives it meaning: an unjudgeable item is recorded by its stage and the revision commits; every other failure leaves the Source Unit revision uncommitted and the next sync retries it. Each stage records it in its own terms: Support Assessment and its targeted re-check, `UNRESOLVED(capacity)` or `UNRESOLVED(invalid_response)` and KEEP; Change Impact, Support Assessment for that claim after any failure; candidate admission, the Candidate `REJECTED` for this round with reason `capacity_exceeded` or `invalid_response`; Sparse Relation, the Candidate consumed without ADD and without a Review, never read as "no relation proposed", and, because its row would cover every old Memory of the Unit, no DELETE, SUPERSEDE or UPDATE of the Unit executed this round; the same-Unit identity backstop, the Candidate consumed without ADD; Claim Extraction, that ReadingGroup skipped with a diagnostic naming the Source Unit, the ReadingGroup and the reason, while the other groups are extracted. Rerank is one indivisible listwise item that is never split; the search caller passes its deadline, and timeout or invalid output keeps the baseline order as a fixed code rule, not configuration. Independent items, judgment and generation alike (including Claim Extraction and candidate admission), use the item form; Support Assessment uses the ordered-chain form with carried compact state and per-item early exit after the first part of the order; the chain task carries each item's first-part boundary, because a Claim's first part is all changed ReadingGroups plus that Claim's own old-Evidence groups. The runner adds no configuration beyond LiteLLM metadata, the existing overrides and `request_timeout_s`, no output budget or tokens-per-second presizing, no business cache key, no lifecycle state, no per-item model switching and no hidden provider fallback. Partitioning, re-asks and splitting never change coverage, work identity, the result schema or lifecycle meaning. A response that reads into rows is journaled even when some rows are rejected, and each re-ask is its own journaled request, so a retry reuses accepted rows and re-asks without a call; with a deterministic fixture client, results are identical across legal partitions and split points.

## Consequences

- The domain names a classifier role rather than a Jev stage; Jev and a small-model LLM are replaceable adapters at one seam.
- Same-Unit Relation stays sparse Structured-LLM discovery with one completion row per Candidate; a pairwise classifier backend would need its own contract and evaluation.
- No call site handles context overflow or timeouts itself; the per-call-site capacity checks, item and character caps, request splitting and correction loops move into the LLM batch runner.
- One item the model cannot judge, because it alone exceeds capacity or its output stays invalid, never blocks the other items of its Source Unit: each stage records it and the revision commits. Only a transient failure leaves the revision uncommitted for the next sync.
- Change Impact avoids sending every exact-rebound claim to compound Support Assessment while preserving a complete claim manifest over every changed bundle.
- Complete Support Assessment remains one implementation and one validator; classifier outputs do not recreate a second Support engine.
- Stable revision context can be reused by provider prompt caches or classifier shared state without becoming lifecycle state.
- Model/backend changes participate in work identity and require task-specific evaluation.
- Cloud impact: Cloud reaches models through LiteLLM `sap/` routes with environment-only configuration. The runner reads capacity from LiteLLM metadata and existing environment overrides only, wraps the existing structured client without changing its constructor (Cloud's `LiteLlmStructuredClient(...)` call is unchanged; removing the dead `SourceSupportDetector` changes Cloud's `proxy/external_runtime.py` lines 23, 217, 237 and 249 in the same wave as the pin upgrade) and changes no storage protocol. Change Impact and Sparse Relation keep using Cloud's existing Structured LLM route. Isolating an unjudgeable item adds no configuration, storage protocol or HANA change: the new Support reason `invalid_response` is an in-memory result, and admission rejections use the existing audit event. Cloud upgrades the OSS pin; its pinned LiteLLM must expose `get_model_info` and `token_counter`, which the client already uses.

## Non-goals

- no one-size-fits-all inference interface;
- no per-item confidence fallback or hidden model substitution;
- no classifier claim generation, image understanding or complete Support Assessment;
- no semantic retrieval pruning of the same-Unit Relation catalog;
- no output-budget or tokens-per-second configuration;
- no correctness dependency on prompt-cache retention;
- no model-owned Source authority, lifecycle verbs or selector membership;
- no human confirmation stage for ordinary source reconciliation;
- no automatic historical reprocessing when an executor profile changes.
