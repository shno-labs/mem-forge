# Keep Review orchestration outside Memory lifecycle

The unified Review surface spans workbench `MemoryReview` records and projected `LifecycleReview` records, but Review status, decision action, and Memory lifecycle postcondition are distinct concepts. It exposes exactly three decision semantics: `MemoryReview.kind=supersede` chooses the current Memory, including an explicit user correction whose Review pins the incumbent's complete active Support Set; `MemoryReview.kind=cross_source_conflict` classifies an independently supported claim pair; and the separate `LifecycleReview` aggregate gates one complete Source Evidence Plan. `LifecycleReview` is not another `MemoryReview.kind`, and unifying the queue does not introduce a fourth kind or a shared lifecycle transition. Workbench supersede and projected-lifecycle decisions continue through their existing stale-guarded promotion or Lifecycle Plan paths. A cross-source conflict Review instead asks whether the contradiction finding is valid: confirming or dismissing it closes the Review without retiring either independently supported Memory. Choosing one source as authoritative remains gated by explicit Correction Authority rather than being inferred from recency, an LLM, or the Review transport.

Agent assistance uses a bounded Decision Manifest containing exact Review IDs, Decision Fingerprints, actions, notes, and rationale. Validation is read-only and returns a principal-bound HMAC receipt for that exact manifest. Apply requires the receipt and invokes the same single-Review decision interface once per item; the MCP tool is marked destructive and still requires the host agent to obtain explicit confirmation for the displayed cohort. The receipt and per-item results are request orchestration data, not durable batch or lifecycle states. One failed item neither weakens another item's atomicity nor creates a cohort rollback state.

The authenticated request principal is the reviewer of record. Callers may not supply reviewer identity, bypass participant and Source visibility, or resolve a configured-source Review without management authority. Every related challenger is a full participant for visibility, Source management, lifecycle guards, and the immutable Decision Fingerprint. A stale fingerprint fails closed, and replaying an already-applied identical decision is idempotent because terminal Review status is not part of the immutable decision input.

The durable `CONTRADICTS` Evidence Relation remains the classifier audit, while the effective retrieval meaning of a cross-source pair is derived from its Review: `pending` is unconfirmed, `approved` is confirmed, `rejected` is dismissed, and `stale` is stale. Search and Memory detail expose this disposition symmetrically from either Memory together with the counterpart and Review rationale. The context is returned only when both participants and their configured Sources are visible to the caller; a hidden counterpart suppresses the whole pair. This read model does not delete evidence on rejection, invent a conflict Memory, choose a winning Source, or add a Relation or Review state.

The actionable queue derives staleness from each Review's pinned participant versions before exact pagination. Dynamically stale rows are excluded from `open` and may be inspected through the `stale` filter, but a read, migration, or background worker does not terminalize existing pending rows. Durable classification of a historical cohort requires a separately authorized bounded maintenance canary; deploying this feature does not resolve existing Payroll Reviews. An authorized user may explicitly recheck one durably stale, nonterminal `LifecycleReview` proposal through the Review UI or authenticated admin route. Recheck preserves the old Review, reuses its revision-pinned Source Evidence, and creates a new pending Review through a new Lifecycle Plan guarded by the current complete Support set, Memory version, Source Unit revision, Observation revisions, Source gate, and Decision Fingerprint. It does not apply the proposal. This exceptional recovery command is intentionally absent from the general-purpose MCP tool interface; agents handle current pending Reviews but do not guess when stale lifecycle history should be reissued. A stale proposal that would retire or supersede the incumbent is not mechanically refreshed because changed Support topology requires source replanning.

For a destructive workbench supersede decision, the Review compare-and-set, incumbent/challenger/related Memory transitions, relational search projection, and Review-owned vector outbox publication commit in one adapter transaction. The service attempts that durable projection work after commit, and the worker retries failures from committed relational truth. It never compensates the committed transaction, because a losing concurrent caller must not restore snapshots over the winner. The Review outbox's delivery statuses are derived-index infrastructure state, not Memory, Review, Lifecycle Plan, or batch lifecycle state. Projected Lifecycle Reviews continue to use their existing Lifecycle Plan-owned vector outbox; Review IDs are never represented as synthetic Lifecycle Plan IDs.

`propose_memory_correction` is the only public correction command. It always
stages a `user_correction` challenger and supersede Review. When the submitting
principal owns the private Memory or can manage every Source in the incumbent's
active Support Set, the command resolves that Review immediately; otherwise it
leaves the Review pending for an authorized Source manager. Source-backed
correction Reviews pin the canonical Support Set hash. Approval atomically
verifies that hash, makes the old assertions non-current without deleting their
Evidence, promotes the challenger, supersedes the incumbent, and publishes the
Review vector outbox. A changed Support Set makes the Review stale.

This decision adds no Memory, Support, Relation, Lifecycle Plan, or Review status. It supersedes the earlier assumption in ADR 0004 that every Review is one generic current-versus-proposed destructive choice, while preserving ADR 0004's lifecycle planner, gate, Support authority, stale-guard, and outbox contracts.
